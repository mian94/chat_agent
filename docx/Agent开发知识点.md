# Agent 开发知识点

本文档整理前端面试辅导 Agent 项目开发过程中遇到的重要知识点，主要涉及 Agent 架构、记忆系统、LLM 对接等内容。

## 1. 记忆系统

### 1.1 短期上下文记忆 vs 本地存储聊天记录

#### 概念解释

**短期上下文记忆（对话上下文窗口）**

本质：LLM 的工作机制，每次请求时把历史消息一起发送给 API。

```
用户发送第 3 条消息时，实际发送给 DeepSeek API 的内容：

{
  "messages": [
    {"role": "system", "content": "你是前端面试辅导老师..."},  // 系统提示词
    {"role": "user", "content": "什么是闭包？"},              // 第 1 条
    {"role": "assistant", "content": "闭包是指..."},           // 第 2 条
    {"role": "user", "content": "能举个例子吗？"}             // 第 3 条（当前问题）
  ]
}
```

特点：
- 每次请求都携带历史消息，让 LLM "记住"之前的对话
- 有 **token 限制**（DeepSeek 最大 32K token），不能无限携带
- **不持久化**，页面刷新后丢失

**本地存储聊天记录（IndexedDB）**

本质：前端的持久化数据库，用来保存聊天记录。

```
IndexedDB 中存储的数据结构：

会话列表：
├── 会话1 { id, title, mode, messages: [...], createdAt }
├── 会话2 { id, title, mode, messages: [...], createdAt }
└── 会话3 { id, title, mode, messages: [...], createdAt }
```

特点：
- **持久化**，页面刷新后数据还在
- 存储容量大（几百 MB）
- 只是"存数据"，不会自动发送给 LLM

#### 核心区别

| 维度 | 短期上下文记忆 | 本地存储聊天记录 |
|------|---------------|-----------------|
| **本质** | LLM 的工作机制 | 前端的数据持久化 |
| **作用** | 让 LLM "记住"对话 | 让用户"看到"历史 |
| **存储位置** | 每次请求时动态构造 | IndexedDB 持久化 |
| **生命周期** | 请求结束就没了 | 页面刷新还在 |
| **容量限制** | 受 token 限制（32K） | 几百 MB |
| **是否发送给 LLM** | ✅ 是 | ❌ 不直接发送 |

#### 实际开发中的配合

阶段 2 的两个任务（短期上下文记忆 + 本地存储聊天记录）是配合使用的：

```typescript
// 伪代码示例

async function sendMessage(userInput: string) {
  // 1. 从 IndexedDB 读取当前会话的历史消息
  const history = await getMessagesFromIndexedDB(currentSessionId);
  
  // 2. 构造短期上下文（取最近 10 条，避免 token 超限）
  const recentMessages = history.slice(-10);
  
  // 3. 发送给后端（后端再转发给 DeepSeek API）
  const response = await fetch('/api/chat', {
    body: JSON.stringify({
      messages: recentMessages  // ← 这就是"短期上下文"
    })
  });
  
  // 4. 把新消息存入 IndexedDB
  await saveToIndexedDB(currentSessionId, userMessage, assistantMessage);
}
```

简单理解：
- **IndexedDB** = 仓库，存所有历史
- **短期上下文** = 从仓库里取最近几条，发给 LLM

#### 为什么需要两个？

| 场景 | 需要 IndexedDB | 需要短期上下文 |
|------|---------------|---------------|
| 用户刷新页面，想看之前的对话 | ✅ | ❌ |
| 用户追问，LLM 需要理解上下文 | ❌ | ✅ |
| 用户想删除某条历史消息 | ✅ | ❌ |
| 对话太长，需要截断 | ❌ | ✅ |

## 2. SSE 流式输出

### 2.1 什么是 SSE？

SSE（Server-Sent Events）是一种服务器向客户端推送数据的技术，基于 HTTP 协议。

### 2.2 SSE vs WebSocket

| 特性 | SSE | WebSocket |
|------|-----|-----------|
| 协议 | HTTP | 独立协议（ws://） |
| 方向 | 单向（服务器→客户端） | 双向 |
| 数据格式 | 文本 | 文本/二进制 |
| 浏览器支持 | 所有现代浏览器 | 所有现代浏览器 |
| 适用场景 | 通知、实时数据流、AI 对话 | 聊天、游戏、协同编辑 |

SSE 适合 AI 对话场景，因为：
1. 只需要服务器向客户端推送
2. 基于 HTTP，兼容性好
3. 自动重连机制

### 2.3 SSE 数据格式

```
data: {"type":"delta","content":"你"}

data: {"type":"delta","content":"好"}

data: {"type":"done"}
```

每条消息以 `data: ` 开头，以 `\n\n` 结尾。

## 3. LLM 对接

### 3.1 DeepSeek API 请求格式

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是前端面试辅导老师..."},
    {"role": "user", "content": "什么是闭包？"}
  ],
  "stream": true,
  "temperature": 0.7,
  "max_tokens": 2048
}
```

### 3.2 角色说明

| 角色 | 说明 |
|------|------|
| `system` | 系统提示词，定义 Agent 的身份和行为 |
| `user` | 用户输入 |
| `assistant` | AI 回复 |

### 3.3 Temperature 参数

- **0**：最确定性，适合事实性问答
- **0.7**：平衡创造性和准确性（推荐）
- **1**：最创造性，适合创意写作

## 4. Agent 架构

### 4.1 核心组件

```
┌─────────────────────────────────────────┐
│           Agent 调度引擎                 │
│                                         │
│   ┌──────────┐  ┌──────────┐           │
│   │ 任务规划  │  │ 反思迭代  │           │
│   └──────────┘  └──────────┘           │
│         │                               │
│         ▼                               │
│   ┌─────────────────────────────┐       │
│   │         工具调用             │       │
│   │  ┌──────┐ ┌──────┐ ┌──────┐ │       │
│   │  │搜索  │ │检索  │ │执行  │ │       │
│   │  └──────┘ └──────┘ └──────┘ │       │
│   └─────────────────────────────┘       │
│         │                               │
│         ▼                               │
│   ┌─────────────────────────────┐       │
│   │       LLM 适配层            │       │
│   │     (DeepSeek API)          │       │
│   └─────────────────────────────┘       │
└─────────────────────────────────────────┘
```

### 4.2 工作流程

1. **用户输入** → Agent 接收任务
2. **任务拆解** → 复杂任务分解为多个步骤
3. **判断是否需要工具** → 是则调用工具，否则直接调用 LLM
4. **工具执行** → 执行工具并获取结果
5. **反思迭代** → 判断是否需要继续循环
6. **输出结果** → 返回给用户
