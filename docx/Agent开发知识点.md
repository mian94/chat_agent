# Agent 开发知识点

本文档整理前端面试辅导 Agent 项目开发过程中遇到的重要知识点，主要涉及 Agent 架构、记忆系统、LLM 对接等内容。

## 1. 记忆系统

### 1.1 短期上下文记忆 vs 本地存储聊天记录

#### 概念解释

**短期上下文记忆（对话上下文窗口）**

本质：LLM 的工作机制，每次请求时把历史消息一起发送给 API。

```
用户发送第 3 条消息时，实际发送给 DeepSeek API 的内容：

{
  "messages": [
    {"role": "system", "content": "你是前端面试辅导老师..."},  // 系统提示词
    {"role": "user", "content": "什么是闭包？"},              // 第 1 条
    {"role": "assistant", "content": "闭包是指..."},           // 第 2 条
    {"role": "user", "content": "能举个例子吗？"}             // 第 3 条（当前问题）
  ]
}
```

特点：
- 每次请求都携带历史消息，让 LLM "记住"之前的对话
- 有 **token 限制**（DeepSeek 最大 32K token），不能无限携带
- **不持久化**，页面刷新后丢失

**本地存储聊天记录（IndexedDB）**

本质：前端的持久化数据库，用来保存聊天记录。

```
IndexedDB 中存储的数据结构：

会话列表：
├── 会话1 { id, title, mode, messages: [...], createdAt }
├── 会话2 { id, title, mode, messages: [...], createdAt }
└── 会话3 { id, title, mode, messages: [...], createdAt }
```

特点：
- **持久化**，页面刷新后数据还在
- 存储容量大（几百 MB）
- 只是"存数据"，不会自动发送给 LLM

#### 关系图

```
┌─────────────────────────────────────────────────────────────┐

│         │                                                   │

│   │         IndexedDB (本地存储)             │               │

│   │  会话1:                                  │               │
│   │    msg1: "什么是闭包？"                  │               │

          │

          ▼

│   │  根据 messages 理解上下文，生成回复       │               │
│   │  "当然可以！闭包的例子..."               │               │
│   │                                         │               │
│   └─────────────────────────────────────────┘               │
│         │                                                   │
└─────────┼───────────────────────────────────────────────────┘
          │
          ▼
      前端收到回复，存入 IndexedDB，更新 UI
```

#### 核心区别

| 维度 | 短期上下文记忆 | 本地存储聊天记录 |
|------|---------------|-----------------|
| **本质** | LLM 的工作机制 | 前端的数据持久化 |
| **作用** | 让 LLM "记住"对话 | 让用户"看到"历史 |
| **存储位置** | 每次请求时动态构造 | IndexedDB 持久化 |
| **生命周期** | 请求结束就没了 | 页面刷新还在 |
| **容量限制** | 受 token 限制（32K） | 几百 MB |
| **是否发送给 LLM** | ✅ 是 | ❌ 不直接发送 |

#### 实际开发中的配合

阶段 2 的两个任务（短期上下文记忆 + 本地存储聊天记录）是配合使用的：

```typescript
// 伪代码示例

async function sendMessage(userInput: string) {
  // 1. 从 IndexedDB 读取当前会话的历史消息
  const history = await getMessagesFromIndexedDB(currentSessionId);
  
  // 2. 构造短期上下文（取最近 10 条，避免 token 超限）
  const recentMessages = history.slice(-10);
  
  // 3. 发送给后端（后端再转发给 DeepSeek API）
  const response = await fetch('/api/chat', {
    body: JSON.stringify({
      messages: recentMessages  // ← 这就是"短期上下文"
    })
  });
  
  // 4. 把新消息存入 IndexedDB
  await saveToIndexedDB(currentSessionId, userMessage, assistantMessage);
}
```

简单理解：
- **IndexedDB** = 仓库，存所有历史
- **短期上下文** = 从仓库里取最近几条，发给 LLM

#### 为什么需要两个？

| 场景 | 需要 IndexedDB | 需要短期上下文 |
|------|---------------|---------------|
| 用户刷新页面，想看之前的对话 | ✅ | ❌ |
| 用户追问，LLM 需要理解上下文 | ❌ | ✅ |
| 用户想删除某条历史消息 | ✅ | ❌ |
| 对话太长，需要截断 | ❌ | ✅ |

## 2. SSE 流式输出

### 2.1 什么是 SSE？

SSE（Server-Sent Events）是一种服务器向客户端推送数据的技术，基于 HTTP 协议。

### 2.2 SSE vs WebSocket

| 特性 | SSE | WebSocket |
|------|-----|-----------|
| 协议 | HTTP | 独立协议（ws://） |
| 方向 | 单向（服务器→客户端） | 双向 |
| 数据格式 | 文本 | 文本/二进制 |
| 浏览器支持 | 所有现代浏览器 | 所有现代浏览器 |
| 适用场景 | 通知、实时数据流、AI 对话 | 聊天、游戏、协同编辑 |

SSE 适合 AI 对话场景，因为：
1. 只需要服务器向客户端推送
2. 基于 HTTP，兼容性好
3. 自动重连机制

### 2.3 SSE 数据格式

```
data: {"type":"delta","content":"你"}

data: {"type":"delta","content":"好"}

data: {"type":"done"}
```

每条消息以 `data: ` 开头，以 `\n\n` 结尾。

### 2.4 前端实现

```typescript
const response = await fetch('/api/chat', {
  method: 'POST',
  body: JSON.stringify({ messages, mode })
});

const reader = response.body.getReader();
const decoder = new TextDecoder();

while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  
  const chunk = decoder.decode(value, { stream: true });
  // 解析 SSE 数据...
}
```

## 3. LLM 对接

### 3.1 DeepSeek API 请求格式

```json
{
  "model": "deepseek-chat",
  "messages": [
    {"role": "system", "content": "你是前端面试辅导老师..."},
    {"role": "user", "content": "什么是闭包？"}
  ],
  "stream": true,
  "temperature": 0.7,
  "max_tokens": 2048
}
```

### 3.2 角色说明

| 角色 | 说明 |
|------|------|
| `system` | 系统提示词，定义 Agent 的身份和行为 |
| `user` | 用户输入 |
| `assistant` | AI 回复 |

### 3.3 Temperature 参数

- **0**：最确定性，适合事实性问答
- **0.7**：平衡创造性和准确性（推荐）
- **1**：最创造性，适合创意写作

## 4. Agent 架构

### 4.1 核心组件

```
┌─────────────────────────────────────────┐
│           Agent 调度引擎                 │
│                                         │
│   ┌──────────┐  ┌──────────┐           │
│   │ 任务规划  │  │ 反思迭代  │           │
│   └──────────┘  └──────────┘           │
│         │                               │
│         ▼                               │
│   ┌─────────────────────────────┐       │
│   │         工具调用             │       │
│   │  ┌──────┐ ┌──────┐ ┌──────┐ │       │
│   │  │搜索  │ │检索  │ │执行  │ │       │
│   │  └──────┘ └──────┘ └──────┘ │       │
│   └─────────────────────────────┘       │
│         │                               │
│         ▼                               │
│   ┌─────────────────────────────┐       │
│   │       LLM 适配层            │       │
│   │     (DeepSeek API)          │       │
│   └─────────────────────────────┘       │
└─────────────────────────────────────────┘
```

### 4.2 工作流程

1. **用户输入** → Agent 接收任务
2. **任务拆解** → 复杂任务分解为多个步骤
3. **判断是否需要工具** → 是则调用工具，否则直接调用 LLM
4. **工具执行** → 执行工具并获取结果
5. **反思迭代** → 判断是否需要继续循环
6. **输出结果** → 返回给用户

## 5. 阶段3：Agent 核心能力技术选型

### 5.1 联网搜索工具

#### 搜索API选择

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **SerpAPI** | 稳定可靠，支持多搜索引擎，有免费额度（100次/月） | 付费，免费额度有限 | ⭐⭐⭐⭐ |
| **Bing Web Search API** | 微软提供，免费额度较大（1000次/月），结果质量好 | 需要Azure账号 | ⭐⭐⭐⭐⭐ |
| **Google Custom Search API** | 结果质量最高 | 付费，配置复杂 | ⭐⭐ |
| **DuckDuckGo Instant Answer** | 完全免费，无需API密钥 | 功能有限，结果不够丰富 | ⭐⭐ |

**推荐方案**：**Bing Web Search API**

理由：
1. 免费额度充足（1000次/月），足够开发和演示
2. 微软提供，稳定可靠，文档完善
3. 结果质量好，适合前端面试题搜索
4. 与项目技术栈（Node.js）集成简单

#### 搜索结果处理

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **直接返回给LLM** | 实现简单，LLM能获取完整信息 | 可能超出token限制，增加API成本 | ⭐⭐⭐ |
| **提取关键信息** | 精准控制token使用，提高效率 | 需要额外处理逻辑，可能丢失信息 | ⭐⭐⭐⭐⭐ |
| **保存到本地** | 便于离线查看，减少重复请求 | 增加存储开销，数据可能过期 | ⭐⭐ |

**推荐方案**：**提取关键信息**

理由：
1. 控制token使用，避免超出DeepSeek API限制
2. 提取标题、摘要、链接等关键信息，足够LLM生成回答
3. 与任务规划配合，按需搜索而非全量返回

### 5.2 工具调用可视化

**工具调用循环定义**：Agent架构中的核心机制，指的是LLM在处理用户请求时，可能需要多次调用外部工具来获取信息或执行操作，形成一个“调用-执行-返回-整合”的循环过程。

#### 可视化形式

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **消息气泡内显示** | 直观，用户一眼看到 | 可能干扰正常对话，信息过多时混乱 | ⭐⭐⭐ |
| **侧边栏面板** | 分离清晰，不干扰对话 | 需要额外空间，移动端体验差 | ⭐⭐⭐⭐ |
| **可折叠的日志区域** | 灵活，用户可选择是否展开 | 需要设计折叠/展开交互 | ⭐⭐⭐⭐⭐ |

**推荐方案**：**可折叠的日志区域**

理由：
1. 用户可选择查看或隐藏，不干扰正常对话
2. 与现有聊天界面风格一致，可放在消息气泡下方
3. 移动端友好，折叠后不占用空间
4. 符合PRD中"工具调用可视化面板"的要求

#### 信息详细程度

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **最小化** | 简洁，不干扰用户 | 信息不足，无法了解工具执行细节 | ⭐⭐ |
| **标准** | 平衡信息量和简洁性 | 可能遗漏重要细节 | ⭐⭐⭐⭐⭐ |
| **详细** | 信息完整，便于调试 | 信息过多，可能吓到用户 | ⭐⭐⭐ |

**推荐方案**：**标准（工具名称 + 参数摘要 + 状态）**

理由：
1. 用户能看到Agent在做什么，但不被细节淹没
2. 开发时可通过调试模式查看详细信息
3. 符合PRD中"工具调用日志"的要求

### 5.3 调试模式

#### 调试信息存储

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **仅控制台输出** | 简单，无存储开销 | 无法持久化，刷新后丢失 | ⭐⭐⭐ |
| **保存到文件** | 便于后续分析，可分享 | 增加IO开销，需要文件管理 | ⭐⭐⭐⭐ |
| **保存到IndexedDB** | 与项目技术栈一致，前端可查看 | 增加数据库负担，数据量大时性能下降 | ⭐⭐⭐⭐⭐ |

**推荐方案**：**保存到IndexedDB**

理由：
1. 与项目现有技术栈一致（已有IndexedDB存储）
2. 前端可直接查看调试日志，无需额外工具
3. 可按会话存储，便于追溯
4. 开发期间可随时查看，生产环境可关闭

#### 调试模式开关

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **环境变量** | 安全，适合生产环境 | 开发时需重启服务 | ⭐⭐⭐⭐ |
| **前端配置** | 灵活，可实时切换 | 可能暴露敏感信息，用户误操作 | ⭐⭐⭐ |
| **后端配置** | 安全，可控 | 需要额外接口，不够灵活 | ⭐⭐⭐⭐⭐ |

**推荐方案**：**环境变量 + 前端开关（组合方案）**

理由：
1. 环境变量控制全局开关，生产环境默认关闭
2. 前端提供调试开关，开发时可实时切换
3. 前端开关仅控制"是否显示调试信息"，不控制"是否记录调试信息"
4. 安全性与灵活性兼顾

### 5.4 任务规划

#### 任务拆分范围

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **所有任务都拆分** | 统一处理，逻辑简单 | 简单任务也拆分，效率低 | ⭐⭐ |
| **仅复杂任务拆分** | 效率高，符合用户直觉 | 需要判断任务复杂度 | ⭐⭐⭐⭐⭐ |
| **用户指定拆分** | 用户控制，灵活 | 增加用户负担，体验差 | ⭐⭐ |

**推荐方案**：**仅复杂任务拆分**

理由：
1. 简单任务（如"解释Vue生命周期"）直接回答，无需拆分
2. 复杂任务（如"帮我准备Vue面试"）自动拆分为多个步骤
3. 通过LLM判断任务复杂度，无需硬编码规则
4. 符合PRD中"复杂需求自动拆解为多步执行"的要求

#### 拆分粒度

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **每个步骤一个API调用** | 粒度细，可控性强 | API调用次数多，成本高 | ⭐⭐⭐ |
| **每个步骤一个工具调用** | 粒度适中，平衡效率和控制 | 可能遗漏细节 | ⭐⭐⭐⭐⭐ |
| **每个步骤多个工具调用** | 粒度粗，效率高 | 可能复杂，难以调试 | ⭐⭐⭐ |

**推荐方案**：**每个步骤一个工具调用**

理由：
1. 粒度适中，既能完成任务，又不过于复杂
2. 每个步骤有明确的输入输出，便于调试
3. 与反思迭代配合，每个步骤后判断是否需要继续
4. 符合PRD中"分步执行，每步输出中间结果"的要求

### 5.5 反思迭代

**反思迭代机制定义**：Agent架构中的智能决策环节，指的是LLM在工具执行完成后，对结果进行评估和反思，判断是否需要继续调用其他工具或调整策略，以确保任务高质量完成。

#### 反思判断标准

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **基于工具返回结果** | 简单，逻辑清晰 | 可能不够智能，误判 | ⭐⭐⭐ |
| **基于LLM判断** | 智能，能理解上下文 | 增加API调用，成本高 | ⭐⭐⭐⭐⭐ |
| **基于预设规则** | 稳定，可预测 | 可能不够灵活，规则难覆盖所有情况 | ⭐⭐⭐⭐ |

**推荐方案**：**基于LLM判断**

理由：
1. LLM能理解工具返回结果的含义，判断是否满足需求
2. 能根据上下文决定是否需要继续搜索或执行其他工具
3. 与任务规划配合，实现真正的"反思迭代"
4. 符合PRD中"工具返回结果后自动判断是否需要进一步操作"的要求

#### 循环次数限制

| 方案 | 优点 | 缺点 | 推荐度 |
|------|------|------|--------|
| **无限制** | 灵活，能处理复杂任务 | 可能无限循环，成本不可控 | ⭐⭐ |
| **固定次数（如3次）** | 稳定，成本可控 | 可能过早终止，任务未完成 | ⭐⭐⭐⭐ |
| **动态次数（基于任务复杂度）** | 智能，效率高 | 实现复杂，需要判断任务复杂度 | ⭐⭐⭐⭐⭐ |

**推荐方案**：**固定次数（3-5次）+ 动态判断**

理由：
1. 设置最大循环次数（如5次），防止无限循环
2. 在循环次数内，由LLM判断是否需要继续
3. 达到最大次数后，强制输出当前结果
4. 平衡灵活性和安全性

## 6. 工具调用调试模式详解

### 6.1 什么是工具调用调试模式？

工具调用调试模式是一种**开发和调试辅助功能**，用于记录和展示Agent内部的完整工具调用链路，帮助开发者理解和优化Agent的行为。

### 6.2 调试模式记录的内容

根据PRD描述，调试模式会记录以下完整链路：

```
1. LLM 决策 → 2. 工具选择 → 3. 参数构造 → 4. 执行结果 → 5. 反思判断
```

具体来说：

| 阶段 | 记录内容 | 示例 |
|------|----------|------|
| **LLM 决策** | LLM决定需要调用工具的原因 | "用户询问Vue3最新特性，需要联网搜索获取最新信息" |
| **工具选择** | LLM选择的具体工具 | `web_search` |
| **参数构造** | 传递给工具的参数 | `{"query": "Vue3 2024 新特性", "count": 5}` |
| **执行结果** | 工具返回的原始结果 | 搜索结果JSON（包含标题、链接、摘要等） |
| **反思判断** | LLM对结果的评估和下一步决定 | "搜索结果包含3个相关链接，信息足够，无需继续搜索" |

### 6.3 调试模式的作用

1. **开发阶段**：
   - 理解Agent如何做出决策
   - 排查工具调用失败的原因
   - 优化工具参数和返回结果处理
   - 验证任务规划和反思逻辑是否正确

2. **演示阶段**：
   - 向他人展示Agent的工作原理
   - 体现项目的Agent架构设计能力
   - 作为简历作品集的技术亮点

3. **维护阶段**：
   - 快速定位问题
   - 分析Agent行为异常的原因

### 6.4 调试模式设计原则

#### 原则一：双重控制机制

调试模式采用前端开关和后端环境变量双重控制机制：
- **前端开关**：用户可以在界面上实时开启/关闭调试模式，控制是否在界面上显示调试日志
- **后端环境变量**：通过`AGENT_DEBUG_MODE`环境变量控制是否在后端输出调试日志
- **双重控制**：任一开关开启都会输出调试日志，确保开发和生产环境的灵活性

#### 原则二：最小化性能影响

- 调试日志的记录和展示不应显著影响系统性能
- 在生产环境中，默认关闭调试模式，避免不必要的开销
- 调试日志仅在开发和调试阶段使用

#### 原则三：信息完整性

- 调试日志应记录完整的工具调用链路，包括LLM决策、工具选择、参数构造、执行结果、反思判断
- 信息应足够详细，便于开发者理解和排查问题
- 同时避免信息过载，保持日志的可读性

#### 原则四：用户友好性

- 调试日志应以用户友好的方式展示，避免暴露技术细节
- 提供展开/折叠功能，让用户选择是否查看详细信息
- 使用清晰的图标和颜色区分不同类型的调试事件

### 6.5 调试事件类型

调试事件是调试日志的基本单位，用于记录Agent工具调用过程中的关键节点。项目中定义了以下四种调试事件类型：

#### 1. tool_call（工具调用）

**含义**：记录LLM决定调用工具的时刻

**包含信息**：
- 调用的工具名称（如`web_search`、`task_planner`等）
- 传递给工具的参数（如搜索关键词、任务描述等）
- 调用时间戳

**作用**：帮助开发者了解LLM选择了哪个工具，以及传递了什么参数

#### 2. tool_result（工具结果）

**含义**：记录工具执行完成的时刻

**包含信息**：
- 工具名称
- 执行结果（成功/失败）
- 返回的数据（如搜索结果、任务拆分结果等）
- 执行耗时

**作用**：帮助开发者了解工具执行的结果和性能

#### 3. reflection（反思判断）

**含义**：记录LLM对工具结果进行反思和判断的时刻

**包含信息**：
- 反思内容（如“搜索结果包含3个相关链接，信息足够”）
- 下一步决策（如“继续执行下一步”或“需要补充信息”）

**作用**：帮助开发者了解LLM的决策过程和反思逻辑

#### 4. task_plan（任务规划）

**含义**：记录任务拆分和规划的时刻

**包含信息**：
- 任务拆分结果（如将“准备Vue面试”拆分为4个步骤）
- 每个步骤的描述

**作用**：帮助开发者了解任务拆分的逻辑和步骤

### 6.6 什么是调试模式开关？

调试模式开关是**控制调试信息是否记录和展示的机制**。

#### 为什么需要开关？

1. **生产环境**：不需要调试信息，避免性能开销和信息泄露
2. **开发环境**：需要调试信息，便于开发和测试
3. **演示环境**：可选择性展示，突出重点

#### 开关的两种层面

| 层面 | 作用 | 控制内容 |
|------|------|----------|
| **后端开关** | 控制是否记录调试信息 | 决定是否将调试信息保存到IndexedDB |
| **前端开关** | 控制是否显示调试信息 | 决定是否在界面上展示调试日志 |

#### 组合使用场景

| 后端开关 | 前端开关 | 效果 |
|----------|----------|------|
| 开启 | 开启 | 记录 + 显示（开发调试） |
| 开启 | 关闭 | 记录但不显示（后台收集） |
| 关闭 | 关闭 | 不记录不显示（生产环境） |

## 7. API调用 vs 工具调用 详解

### 7.1 先理解两个核心概念

#### API调用 = 调用大语言模型（DeepSeek）

```
前端 → 后端 → DeepSeek API → 返回AI生成的回复
```

**作用**：让AI思考、生成文本、做决策

**例子**：
- 用户问："Vue的生命周期有哪些？"
- 后端调用DeepSeek API
- AI返回："Vue的生命周期包括：beforeCreate、created、beforeMount、mounted..."

#### 工具调用 = 调用后端定义的功能

```
AI决定需要工具 → 后端执行工具 → 返回工具执行结果
```

**作用**：让AI能"动手做事"，而不仅仅是"动嘴说话"

**例子**：
- 用户问："搜索最新的Vue3面试题"
- AI决定需要调用`web_search`工具
- 后端执行搜索，返回搜索结果
- AI根据搜索结果生成回答

### 7.2 用"做饭"来类比

把Agent想象成一个厨师：

| 角色 | 对应Agent | 作用 |
|------|-----------|------|
| **厨师（AI）** | DeepSeek API | 思考、决策、生成回答 |
| **厨房工具（刀、锅、烤箱）** | 后端工具 | 执行具体操作（搜索、计算等） |
| **做一道菜** | 完成一个任务 | 可能需要多次使用工具和多次思考 |

#### 场景：做一道"番茄炒蛋"

**方式A：粗粒度（每个步骤一个API调用）**
```
1. 厨师思考：需要准备番茄、鸡蛋、调料 → API调用1
2. 厨师动手：切番茄、打鸡蛋 → 工具调用（切菜工具）
3. 厨师思考：可以开始炒了 → API调用2
4. 厨师动手：炒菜 → 工具调用（炒锅）
5. 厨师思考：快熟了，可以调味 → API调用3
6. 厨师动手：加调料 → 工具调用（调料瓶）
7. 厨师思考：完成了 → API调用4
```
**特点**：厨师每做一步都要"想一想"，API调用次数多

**方式B：细粒度（每个步骤一个工具调用）**
```
1. 厨师思考：需要准备番茄、鸡蛋、调料，然后切、炒、调味 → API调用1
2. 厨师动手：切番茄 → 工具调用1
3. 厨师动手：打鸡蛋 → 工具调用2
4. 厨师动手：炒菜 → 工具调用3
5. 厨师动手：加调料 → 工具调用4
6. 厨师思考：完成了 → API调用2
```
**特点**：厨师想一次，做很多步，API调用次数少

### 7.3 拆分粒度的具体含义

#### 粒度1：每个步骤一个API调用（最细粒度）

```
用户："帮我准备Vue面试"

步骤1: AI思考 → 需要搜索Vue3最新特性 → API调用1
步骤2: 执行搜索 → 工具调用（web_search）
步骤3: AI思考 → 搜索结果已获得，需要整理知识点 → API调用2
步骤4: 执行整理 → 工具调用（知识整理）
步骤5: AI思考 → 知识点已整理，需要生成练习题 → API调用3
步骤6: 生成练习题 → 工具调用（题目生成）
步骤7: AI思考 → 练习题已生成，任务完成 → API调用4
```

**API调用次数**：4次
**工具调用次数**：3次

#### 粒度2：每个步骤一个工具调用（中等粒度）

```
用户："帮我准备Vue面试"

步骤1: AI思考 → 需要搜索、整理、生成题目 → API调用1
步骤2: 执行搜索 → 工具调用1（web_search）
步骤3: 执行整理 → 工具调用2（知识整理）
步骤4: 生成练习题 → 工具调用3（题目生成）
步骤5: AI思考 → 任务完成 → API调用2
```

**API调用次数**：2次
**工具调用次数**：3次

#### 粒度3：每个步骤多个工具调用（最粗粒度）

```
用户："帮我准备Vue面试"

步骤1: AI思考 → 需要搜索、整理、生成题目 → API调用1
步骤2: 执行搜索+整理+生成题目 → 工具调用1（复合工具）
步骤3: AI思考 → 任务完成 → API调用2
```

**API调用次数**：2次
**工具调用次数**：1次

### 7.4 粒度与成本、效率的关系

| 粒度 | API调用次数 | 工具调用次数 | 成本 | 效率 | 灵活性 |
|------|-------------|--------------|------|------|--------|
| **最细** | 多 | 多 | 高 | 低 | 高 |
| **中等** | 中 | 中 | 中 | 中 | 中 |
| **最粗** | 少 | 少 | 低 | 高 | 低 |

#### 为什么粒度影响成本？

1. **API调用成本**：每次调用DeepSeek API都要消耗token（按量计费）
2. **工具调用成本**：每次工具调用可能涉及外部API（如搜索API有免费额度限制）

#### 为什么粒度影响效率？

1. **最细粒度**：每一步都要等AI思考，响应慢
2. **最粗粒度**：AI想一次，执行很多步，响应快

#### 为什么粒度影响灵活性？

1. **最细粒度**：每一步后AI都能调整计划，适应变化
2. **最粗粒度**：计划一旦制定，中途难以调整

### 7.5 实际例子对比

#### 用户请求："搜索Vue3面试题，整理成知识点，生成练习题"

**方式A：最细粒度（每个步骤一个API调用）**
```
AI思考1：需要搜索 → API调用1
搜索：web_search("Vue3面试题") → 工具调用1
AI思考2：搜索完成，需要整理 → API调用2
整理：knowledge_organize(搜索结果) → 工具调用2
AI思考3：整理完成，需要生成题目 → API调用3
生成：question_generator(知识点) → 工具调用3
AI思考4：任务完成 → API调用4
```
- **总API调用**：4次
- **总工具调用**：3次
- **特点**：AI每一步都确认，最安全但最慢

**方式B：中等粒度（每个步骤一个工具调用）**
```
AI思考1：需要搜索、整理、生成题目 → API调用1
搜索：web_search("Vue3面试题") → 工具调用1
整理：knowledge_organize(搜索结果) → 工具调用2
生成：question_generator(知识点) → 工具调用3
AI思考2：任务完成 → API调用2
```
- **总API调用**：2次
- **总工具调用**：3次
- **特点**：AI想一次，执行多步，平衡效率和灵活性

**方式C：最粗粒度（复合工具）**

- **特点**：一个工具完成所有事情，最快但最不灵活

## 9. Function Calling机制

### 9.1 定义

Function Calling（函数调用）是大语言模型（如DeepSeek）提供的一种机制，允许LLM在生成回答时调用外部函数或工具来获取信息或执行操作。这是Agent架构的核心能力之一，使得LLM能够“动手做事”，而不仅仅是“动嘴说话”。

### 9.2 工作原理

1. **工具定义**：开发者在API请求中定义可用的工具列表，包括工具名称、描述、参数等
2. **LLM决策**：当LLM接收到用户请求时，会分析是否需要调用工具
3. **返回tool_calls**：如果需要调用工具，LLM会返回`tool_calls`字段，指定要调用的工具和参数
4. **工具执行**：后端接收到`tool_calls`后，执行相应的工具
5. **结果返回**：将工具执行结果返回给LLM
6. **生成回答**：LLM根据工具返回的结果，生成最终的回答

### 9.3 API格式

DeepSeek API的Function Calling格式如下：

```json
{
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "web_search",
        "description": "搜索互联网获取最新信息",
        "parameters": {
          "type": "object",
          "properties": {
            "query": { "type": "string", "description": "搜索关键词" },
            "count": { "type": "number", "description": "返回结果数量" }
          },
          "required": ["query"]
        }
      }
    }
  ]
}
```

### 9.4 关键特点

- **动态决策**：LLM根据上下文动态决定是否需要调用工具
- **参数传递**：LLM可以传递复杂的参数给工具
- **结果整合**：LLM能够理解工具返回的结果，并生成连贯的回答
- **多工具支持**：可以同时定义多个工具，LLM根据需要选择调用

## 10. 流式响应中tool_call处理

### 10.1 背景

DeepSeek API支持流式响应（stream），这意味着AI的回复是“一个字一个字”发过来的。对于工具调用，AI也是分多次发送的，需要将这些“碎片”拼接起来，形成完整的工具调用请求。

### 10.2 流式响应的特点

1. **增量返回**：工具调用信息不是一次性返回的，而是分多次返回
2. **ID可能缺失**：`tool_call`的`id`字段可能在第一次出现时提供，后续的增量数据中不再包含
3. **参数拼接**：工具调用的参数是分多次返回的，需要拼接起来
4. **索引标识**：每个工具调用有一个`index`字段，用于标识是第几个工具调用

### 10.3 处理策略

#### 使用index跟踪

由于`id`字段可能缺失或重复，使用`index`来跟踪同一个工具调用：
- 第一次出现时，`index`对应的数组位置是空的，需要创建新的记录
- 后续出现时，`index`对应的数组位置已经有值了，需要合并参数

#### 过滤空位

使用`index`赋值可能会在数组中留下空位，需要过滤掉：
```typescript
const validToolCalls = toolCalls.filter(tc => tc != null);
```

### 10.4 关键点

- **index是DeepSeek提供的**：用于标识“这是第几个工具调用”
- **第一次出现时创建记录**：如果`toolCalls[index]`不存在，创建新的记录
- **后续出现时合并参数**：如果`toolCalls[index]`已存在，将新的参数追加到已有的参数后面
- **最后过滤空位**：使用`filter`过滤掉数组中的`null`或`undefined`

## 11. IndexedDB数据持久化注意事项

### 11.1 背景

IndexedDB是浏览器提供的本地数据库，用于存储大量数据。在本项目中，用于存储会话和消息数据。但是IndexedDB有一个重要的限制：**只能存储可序列化的数据**。

### 11.2 什么是可序列化？

可序列化是指数据可以被转换为JSON格式，并且可以被完整地还原回来。

**可序列化的数据类型**：
- 简单类型：字符串、数字、布尔值、null
- 简单对象：只有键值对，没有函数
- 数组：元素都是可序列化的

**不可序列化的数据类型**：
- 包含函数的对象
- 包含循环引用的对象
- 包含特殊类型（如Date、RegExp、Map、Set等）的对象
- 包含DOM元素的对象

### 11.3 常见问题：DataCloneError

当尝试将不可序列化的数据保存到IndexedDB时，会抛出`DataCloneError`错误：
```
Uncaught (in promise) DataCloneError: Failed to execute 'put' on 'IDBObjectStore': [object Array] could not be cloned.
```

### 11.4 解决方案

#### 方案一：移除不可序列化字段

在保存数据之前，移除不可序列化的字段：
```typescript
const { debugEvents, ...messageForDB } = message;
await db.put('messages', messageForDB);
```

#### 方案二：深拷贝并过滤

使用深拷贝函数，并过滤掉不可序列化的字段：
```typescript
function cloneForDB(obj) {
  return JSON.parse(JSON.stringify(obj));
}
```

#### 方案三：自定义序列化

对于特殊类型，提供自定义的序列化和反序列化方法：
```typescript
// 序列化
const serialized = {
  ...data,
  date: data.date.toISOString()
};

// 反序列化
const deserialized = {
  ...data,
  date: new Date(data.date)
};
```

### 11.5 最佳实践

1. **数据设计阶段**：设计数据结构时，避免使用不可序列化的类型
2. **保存前检查**：在保存数据之前，检查是否包含不可序列化的字段
3. **错误处理**：捕获`DataCloneError`错误，并提供友好的错误提示
4. **临时数据处理**：对于临时数据（如调试日志），可以选择不保存到IndexedDB
5. **测试验证**：在开发过程中，测试数据是否可以正确保存和读取

### 11.6 本项目中的应用

在本项目中，`debugEvents`字段包含不可序列化的对象（如`parameters`和`result`字段是`any`类型），因此在保存消息到IndexedDB时需要移除：

```typescript
// saveMessage函数
export async function saveMessage(message) {
  const db = await getDB();
  const { debugEvents, ...messageForDB } = message;
  await db.put('messages', messageForDB);
}

// saveSession函数
export async function saveSession(session) {
  const db = await getDB();
  const tx = db.transaction(['sessions', 'messages'], 'readwrite');
  
  const { messages, ...meta } = session;
  await tx.objectStore('sessions').put(meta);
  
  for (const msg of messages) {
    const { debugEvents, ...msgForDB } = msg;
    await tx.objectStore('messages').put({ ...msgForDB, sessionId: session.id });
  }
  
  await tx.done;
}
```

这样可以确保数据可以安全地保存到IndexedDB，同时保留调试日志在内存中的完整信息。
